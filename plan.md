# DAEMatch implementation plan

## Product and scope

Build DAEMatch (Developer And Employer Match) for Amana Software (AMS), with the tagline “Where Developers Meet Employers.” It serves Somali developers first, then African developers, then the global tech market. Deliver a responsive public marketing site plus authenticated developer and employer experiences with role-specific behavior, job applications, networking models, and explainable skills-based matching. Preserve the complete page, model, endpoint, pricing, and algorithm requirements from the supplied specification in `TODO.md` after plan approval.

## Implementation approach

- **Frontend:** React with Vite (TypeScript for maintainability), responsive accessible pages and components. Use client-side routing, a shared API client, role-aware navigation and protected routes. Store JWT access/refresh tokens in `localStorage` as specified, attach Bearer tokens to API requests, and expose login, registration, logout, error, loading and empty states.
- **Backend:** Django + Django REST Framework, custom `AbstractUser` with developer/employer roles, and `djangorestframework-simplejwt`. Enforce role permissions on write and employer-only/developer-only views. Use Django password hashing and server-side validation.
- **Database:** PostgreSQL with deterministic Django migrations. Use a local PostgreSQL instance for development preview where available; configure the production service to use Railway's PostgreSQL `DATABASE_URL`. Do not substitute the Manus-managed MySQL database. Store local-only environment values outside Git; include an `.env.example` with placeholders, never credentials.
- **CV upload and privacy:** Let developers upload, replace, remove, preview and download one PDF or DOCX CV up to 5 MiB. Validate file extension, signature and DOCX structure on the server, sanitize filenames, and store the bytes and metadata in PostgreSQL rather than ephemeral Railway disk or a public URL. Return metadata only in profile/application APIs. Fetch previews through authenticated endpoints: render PDFs inline and show bounded DOCX text as escaped, read-only text. Apply private no-store headers; only the owning developer or an employer who received that developer's application for one of its jobs may preview/download the file.
- **Matching:** Calculate required-skill coverage from normalized, unique skill names: matched unique job requirements ÷ unique job requirements × 100, rounded to one decimal. Unrelated extra profile skills do not lower a score; return 0 when there are no profile skills or no role requirements. Reuse the same matching service for developer job matches, employer applicant ranking and high-match alerts. Match legend thresholds are green at 75%+, orange at 50–74%, and red below 50%. Explain each score with matched/missing requirements and exact counts; recalculate from current profile skills and job requirements.
- **Preview:** Vite serves the browser UI on the configured 3000 port; Django serves its REST API on a separately declared 8000 runtime endpoint. Vite proxies `/api` to Django for same-origin browser calls. This is the project's development/Preview arrangement, not the production host.
- **External deployment targets:** Include Railway backend and Vercel frontend configuration/documentation and example environment variables. Keep PostgreSQL external to the managed Manus database. Actual third-party deployment requires suitable account access, provider setup, and production environment values; do not claim publication unless it succeeds.

## Functional design

The public landing page carries AMS branding, requested CTA and role paths, feature and four-step explainer sections, audience cards, and a pricing section clearly marked “Pricing is coming soon”; do not show plan dollar amounts on the site until they are announced. Proposed business-model tiers remain planning-only: Developer Free, Developer Pro $9/month, Employer Basic $49/month, Employer Pro $99/month. Pricing is informational; payment processing is outside the supplied feature scope.

Registration uses separate developer and employer forms. The developer form collects username, email, password and location. The employer form collects email, company website, company name, location and password, without asking for a username; the backend generates an internal unique username from the employer email to satisfy Django's `AbstractUser`, and employer login accepts email while developer login accepts username. Persist employer company fields on the account and expose them in the profile. Both successful registrations return the user to the shared login page. Login, logout, dashboards, jobs/search/filter, developer matching, profile editing and skill management, employer job/applicant views, and connection flows otherwise follow the supplied actors, fields, API paths, states and role restrictions. For developer applications, clicking Apply opens a job-details confirmation dialog showing employer, location type, salary, posting date, full description and required skills; only the dialog's explicit Apply confirmation submits the application, while closing it cancels. After success show the Applied state. Include the requested Referral model. Do not represent placeholder counts as real users or activity; use database-derived counts or clearly marked empty states.

Employer job management adds `PATCH /api/jobs/<id>/` and `DELETE /api/jobs/<id>/` for the owning employer only. The existing job form is reused for edits; deletion requires confirmation that clearly warns all applications for that job will also be removed by the existing cascade relation.

The employer dashboard keeps its top-five AI-ranked applicant preview and adds a clearly labelled control to load/view every application received for the signed-in employer's jobs using the existing employer-filtered `GET /api/jobs/applications/` endpoint. The complete list has Review, Accepted and Connect filters; Connect is hydrated from pending requests in either direction and accepted connections between the employer and developer. A search input narrows the current list by developer username, job title, skills, location or application status, and composes with the selected filters. Selecting Review opens a keyboard-accessible developer report with the available profile details (bio, location, years of experience, skills and GitHub/LinkedIn links), applied job, cover letter, match score and current status; pending applications are marked reviewed while accept/reject/connect actions remain available.

Add persistent in-app notifications in a dedicated Django app. Application lifecycle events reference their job application, while high-match events reference the matched job. `GET /api/notifications/` returns only the signed-in user's latest notifications and unread count; `POST /api/notifications/<id>/read/` marks one as read, and `POST /api/notifications/read-all/` marks that user's notifications read. A newly created application notifies only the employer that owns its job; transitioning an application to accepted or rejected notifies only the applicant developer. The authenticated workspace notification center shows a role-safe, recipient-scoped unread count and recent messages, supports marking one or all read, and refreshes on focus and periodically. New-application notifications link employers to the existing Incoming applications section on their dashboard; acceptance notifications link developers to the application chat.

Send email for application-received, accepted and rejected events using the existing Django mail settings. Create a database-backed `EmailDelivery` outbox record alongside each newly created notification; enqueue delivery asynchronously only after the transaction commits. Persist delivery status, attempt count, next retry time and last error so a process restart cannot erase pending work. Retry transient failures with backoff and provide `manage.py send_pending_notification_emails` for scheduled recovery; delivery failure must never undo the application or status change. Use the configured `FRONTEND_URL` for links. Direct Gmail SMTP with the provided app password did not deliver, so use a Django Gmail API OAuth2 email backend that calls `users.messages.send` with the send-only `https://www.googleapis.com/auth/gmail.send` scope and an offline refresh token. Select it only when all three OAuth client ID, client secret and refresh-token values are present; refresh access tokens at send time, keep credentials in protected runtime values, sanitize provider errors, and reject incomplete OAuth configuration. Preserve generic SMTP when no OAuth configuration is present, with the console backend as local default. The send-only Gmail scope is sensitive and public OAuth applications may require Google verification. A Workspace SMTP relay is an alternative only after a Workspace administrator configures the relay, allowed senders and TLS/IP authentication; do not assume a stable cloud egress IP. Protected Webdev runtime values do not automatically configure the separately hosted Railway service. Production also schedules the outbox command.

High-match alerts use the same required-skill coverage function as the matches API. Re-evaluate a developer/job pair after developer skills are added or removed and when an employer creates or edits a job; if the score is strictly greater than 85% and the developer has not applied, persist one job-targeted notification and one email-outbox record for that developer/job pair. Store the score snapshot, link to the specific match, suppress repeated alerts for that pair, and do not create alerts as a side effect of GET requests.

Once an application is accepted, the applicant and owning employer may exchange persistent messages for that application through `GET|POST /api/jobs/applications/<id>/messages/`. Store messages against the application; authorize only those two participants and only while the application is accepted. Add a shared `/messages` page/navigation link for both roles that lists accepted applications, loads and sends messages, polls the open conversation, and opens a specific thread from acceptance notifications/email. Pending and rejected applications do not expose chat.

Password recovery adds a public Forgot password form and reset-password screen. The API queues the same asynchronous work path for every submitted address, sends only when an active account matches, and returns the same generic response without waiting for the account lookup or email delivery. The reset link uses an expiring Django token and the configured frontend origin (`FRONTEND_URL`). Token validation and password change occur atomically while holding a user-row lock, so simultaneous confirmations cannot reuse a token. Validate new passwords with Django's configured validators. Local development uses the console email backend; hosted deployments can configure SMTP with protected environment values. Never derive the public reset URL from the internal request Host.

## Design system

- **Design movement:** Contemporary, editorial product design for an Africa-first professional network.
- **Core principles:** Credible over flashy; skills and outcomes first; clear separation of developer/employer journeys; accessible on mobile and desktop.
- **Color philosophy:** Keep the specified #1565c0 as the unmistakable brand blue for trust, focus and action; pair it with warm off-white surfaces, deep ink/navy text and restrained neutral borders. Use semantic match colors only where required by the match-score legend.
- **Layout paradigm:** An asymmetrical, editorial landing hero and vertically sequenced storytelling; once signed in, a compact persistent workspace rail with a wide, information-rich content area, adapting to a mobile bottom/compact navigation rather than shrinking a desktop grid.
- **Signature elements:** A bridge/paired-node mark suggesting talent meeting opportunity; crisp blue skill chips; ranked match cards with restrained animated score bars.
- **Interaction philosophy:** Direct, low-friction actions, visible applied/active states, inline validation and keyboard-visible focus; no action should depend on color alone.
- **Animation:** Restore the earlier hero style from the existing animation commit: a subtle orbital motif with gently floating developer, AI-fit and Product Engineer cards and a short match-bar reveal, rather than the newer travelling connector sequence. Preserve the static reduced-motion state and readable labels; reveal “One platform, two clear paths” in sequence.
- **Typography system:** Manrope for display hierarchy with Inter for body/UI, using sans-serif fallbacks; large concise editorial headlines, compact readable labels, and numeric emphasis for match scores.
- **Brand essence:** “A skills-first bridge from Somali and African tech talent to employers hiring for what people can do.” Personality: capable, welcoming, ambitious.
- **Brand voice:** Clear, confident, human and action-oriented. Example lines: “Let your skills lead the way.” “Find roles that fit your stack.”
- **Wordmark & logo:** A custom “DAEMatch” wordmark paired with a compact bridge/paired-node glyph; AMS appears as the company signature in the footer.
- **Signature brand color:** #1565c0, retained exactly as requested.

## Project structure

- `frontend/`: Vite app, React routes, design tokens, shared components, role-specific pages, API client, and `public/manus-routes.json`.
- `backend/`: Django project settings/URLs plus apps for accounts/profiles, jobs/applications/messages, networking/referrals, persistent recipient-scoped notifications and an email outbox/retry command, and skill-based matching; migrations and focused API tests live beside their apps.
- `frontend/`: shared authenticated notification center and role-neutral messages page join the existing employer/developer routes, typed API client and workspace styles.
- Root: pinned Node package-manager metadata and scripts, Python requirements, deployment examples/configuration, `.gitignore`, `.env.example`, project README, `plan.md`, and the detailed outcome-based `TODO.md`.

## Decisions and material constraints

The user's explicitly selected credentials flow is username/email/password with SimpleJWT, so it takes precedence over the platform's default login provider. The user explicitly selected PostgreSQL, so the platform's managed MySQL database is not enabled. The user selected Railway and Vercel as hosting targets; provider-specific deployment readiness is in scope, but live third-party deployment is contingent on accessible accounts and production values. Do not add billing/Stripe behavior because the request specifies pricing tiers but no checkout flow.
